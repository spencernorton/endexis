## 2.5.1 — 2026-11-25 — multiturn dev scoring (the package still says 2.4.1)

### Fixed
- An override value with a filler adverb before it (*cleanly stepdown*, *directly stepdown*; `explicitly`,
  `specifically`, `directly`, `verifiably`, `accurately`, `cleanly`, `reliably`, `precisely`) resolves like the bare
  value, unless a tenant or catalog value is spelled that way (none is). The v2.3 corpus's firewall rewording put these
  words into the multiturn prompts, and its parser carried them into the override values of the training targets and
  `oof_eval_v2_3`'s ground truth alike, so the models write them too. Since the 2026-11-12 strict compiler they were
  refused, from the model's IR and from the prompt's own parse, so every model failed all 36 multiturn dev items.
  Cleaning the ground truth alone would have changed no score: Pass@1 compiles the prompt and the model's IR, not the
  ground truth.
- Rescored under this code (`data/multiturn_dev_rescore_receipt.json`, one RTX 4070 Ti SUPER, merged BF16, the dev set
  unchanged): v2.3.0 Pass@1 0.9697 (multiturn 32/36), exactly its published 2026-11-11 score, from 0.7273 under the
  2026-11-12 code; the v2.5.0 candidate 0.9924 (multiturn 35/36), from 0.7273. Canonical and collision slices are 1.0
  for both. So v2.5.0 does not regress on multi-turn refinement.

## 2.5.0 — 2026-11-24 — upload-edit cases (the v2.5.0 model's data and scripts; the package still says 2.4.1)

### Added

  (`ENDEXIS_UPLOAD_SUGGEST`). Each case is a synthetic `.dareport` or `.daquery` (written by `DA2ReportGenerator`),
  up to three earlier messages, and the latest one; the target is the plain ask the latest meant (*remove Enc Loc
  Room* for *lose the room column*), or `null` when it asks for no change (a question, *don't add the MRN*, an
  unsure ask, a stand-in owner group). endexis-chat's own rules label every case: the target, sent to them on the
  same file and history, makes exactly the intended changes, and the expected changes are the rules' own output.
  - `scripts/build_upload_edit_cases.py` builds them, prompting with endexis-chat's `edit_prompt` (`--chat-app`), so
    the model trains on the prompt the chat sends. Rerunnable: it replaces its own rows.
  - `data/sft_train_v1.jsonl`: 2,600 rows (547 the rules already make, 1,486 they hold or miss that meant a change,
    567 that meant none). `data/dpo_contrastive_v1.jsonl`: 650 pairs (refusing a meant change, the opposite change,
    the wrong column, a proposal where none was meant, a stand-in owner).
  - `data/eval_upload_edits_v1.jsonl`: the sealed holdout, 724 cases on other reports and other phrasings (78 / 460 /
    186), with 36 dropped for overlapping training (exact, token bag or 5-gram skeleton of the message, exact or bag
    of the prompt). Firewall hashes and the build receipt sit beside it. The new training rows have no exact, bag or
    skeleton overlap with `eval_postfreeze_v3`'s hashes (the file itself is never opened).
  - `scripts/qualify_upload_edits.py`: `generate` asks a served model for each holdout prompt; `score` runs each reply
    through endexis-chat's own `suggestion()`, so a rewording counts only if the chat would show it.
  - `scripts/train_upload_edits_v2_5.py`: the v2.3 recipe's full-corpus stage on the new corpus (refuses to start if
    either sealed holdout is in the workspace).
  - `scripts/compare_dev_same_code.py`: scores models on `oof_eval_v2_3` under the same code, and compares the
    multiturn IR with the ground truth field by field.
- The v2.5.0 model (`data/upload_edits_v1_qualification_receipt.json`): the stage-1 SFT model, as
  the DPO stage failed the v2.3 gate (val SFT loss 0.118 after DPO, 0.1162 before). On the sealed holdout, served as
  `Q8_0` with endexis-chat's request and the no-change guard: of the 460 held messages that meant a change, 77.8%
  get the right rewording and 3.3% a wrong one (bag F1 0.88, precision 0.99); none of the 186 that meant no change
  gets one (10.2% before the guard, all on *don't …* messages); 55.4% of all held messages get the right one (an
  oracle scores 71.2%), 2.3% a wrong one. p50 730 ms on a shared 8-thread CPU. `Q4_K_M`: 76.1%, 3.5%, bag F1 0.86, p50
  522 ms. v2.3.0, the served model, never rewords (0%).
  On `oof_eval_v2_3` under the same code it matches v2.3.0 (Pass@1 0.7273, element F1 0.697; multiturn IR domain
  1.0, element F1 0.990 vs 0.989, override filters 1.0 for both).
- Known gaps: training and holdout share the plain words for a column (`ALIASES`), so the holdout tests new
  phrasings, files and histories, not new words. The rules misread 18 generated asks as other changes (*can we drop
  the event name?* removed `CE Performed Prsnl Name`; *also the event name* after a removal added `CE Lbl Name`);
  they are left out and listed in the receipt. `oof_eval_v2_3`'s multiturn ground truth carries override values
  like *cleanly stepdown* that the strict compiler rejects since the 2026-11-12 code, so no model passes those 36

## 2.4.1 — 2026-11-23

### Fixed
- `read_da2_file` finds each data set's layout items in one pass, and reads at most 20 of a table's own rows (a grid nested in a cell has rows of its own). Before, every query data set walked the whole layout again, and every table walked every row below it, so a crafted 13 KB `.dareport` took minutes to read, and nested tables still took 2.6 seconds.
- Refused with a reason: layouts with more query data sets than a report can hold queries (20, across the whole file), a member with more than 20,000 XML elements (DA2's own layouts have one to three thousand; a member with over twice that many `<` is refused before it is parsed), a member with more than 40,000 `=` and `#` together, counted before it is parsed (an attribute each, or a character reference that becomes an attribute or an element in an embedded prompt; the real exports have 4,100 at most, and each attribute name in a long namespace takes about 500 bytes, so 210,000 of them grew one read by 120 to 150 MB), a member declared other than XML 1.0 (expat reads XML 1.1 as 1.0, and BIRT's parser doesn't: there a NEL (U+0085) ends a line, so a `//` comment hid a patient filter from this reader only; the real exports are all 1.0), a tag a DA2 reader may read as another (BIRT matches a layout tag by the Java hashCode of its lower case alone, so `<EXPRESSION>`, or `<expressiq0>` of the same hash, is an `<expression>` there: a layout tag must be one of BIRT's own, exactly, and every tag is lower case, as in the real exports), a part read once given twice (BIRT keeps an ex-property's last `<value>`, and the checks read the first; a query's `<operator>`, `<values>`, `<qualification>` and the like, which DA2 writes once and numbers when it repeats them), an expression written as a plain setting (BIRT reads `<property name="expr">`, `<xml-property name="expression">` and the like as the expression whatever the tag, and the checks read `<expression>`: an expression-typed setting must be an `<expression>`, or a list's `<simple-property-list>`, as in the real exports), an extended property holding anything but one ASCII `<name>` and one `<value>` (BIRT sets its name or value from a `<property>` in it, and Java's case-blind match takes a dotless ı for an i), a zip whose entries carry more than 256 bytes of extra fields (DA2 writes none, and Python decodes one in time quadratic in its records) or that holds more than 20 files (both counted from its central directory, before it is opened), a zip member packed other than by deflate (bzip2 and LZMA unpack without a bound before anything counts them; any zip `zipfile` fails on is now a refusal, not an error), a file with more than 100 runtime-prompt texts (the real exports have 7 at most), a data set whose query is written into the layout instead of named by its id, two data sets of one name (BIRT binds a table by the name, so which one it shows can't be told), and an element that gives one setting two values (DA2 writes each once; BIRT reads one of them). Reading a member and each change walk all of it, so the element cap bounds what they cost.
- Refused with a reason: XML that DA2 doesn't write inside a member, namely a comment or processing instruction, text between elements, or an element in another namespace (`xmlns=""` too). BIRT's reader joins an expression's text around a comment and reads an element in another namespace by its name, so `row["Person Id"]<!-- x --> == 12345678` or a second setting in `xmlns=""` was read one way here and another way in DA2. None of the real exports has any.
- Adding to a layout whose element ids run past 18 digits is refused with a reason (DA2 writes ids of a few digits). Each add reads every id as a number to find the next one, so a crafted 2 MB layout of 4,299-digit ids took 0.7 s of CPU an add, twice what the change was charged.
- A name or setting over 1,000 characters is refused with a reason: an attribute or a `<property>`'s text (DA2's are under 80), other than an embedded image's base64 `data`, and an XML namespace over 64 bytes (DA2's are under 60), each `xmlns` measured on its own (an attribute value or text that reads like one can't hide a long one behind it). The parser copies a namespace into every name it qualifies, all through the member, so a 1 MB one took 15 s and an 11 KB file; the check reads the member's bytes once, before the parser sees them. Every read folds and matches each name, so one name of 1.9 MB cost 13 to 25 times its charge, and a 5,000-digit `rowSpan` stopped the read with an error (a span of 0, or of 10 digits or more, given any way, now counts as merging cells).
- A table with more than 20 rows keeps its layout when a column is added, with a note to add it there in DA2, and a column it shows is removed in DA2. Each added column puts a cell in every row, so a forged table with thousands of rows grew past the memory limit in a few changes. DA2's own tables have up to eight rows. A table with more than 200 columns is kept the same way (real exports have up to 51): a removal looks up each row's cell at each place, and a forged table 4,700 columns wide took 11 s a turn. A removal takes its cells out of each row in one pass: taking them out one at a time looked through the row from its start each time, so a 200-column table padded with empty elements cost twice its charge.
- A whole patient name in a filter is refused however it's spelled, like `DOE, JANE` always was:
  - two pieces of a name in one value: `DOE%JANE%`, `D_E%J%`, `DOE%J%`, or the same word twice (`LEE__LEE%` matches `LEE, LEE`). Anything but letters, digits, apostrophes and hyphens separates pieces (a wildcard, a space, a comma, a dot), and a single letter is one. A run of Zs (DA2's test-patient marker) is no piece;
  - or two across the file's filters: a last-name pattern and a first-name one, or the start and the end of a full name (`LEE__%` and `%__LEE`). A piece after `_` wildcards is no start: `SMITH%` with `_______JOHN%` is a whole name. Ranges on a name field follow the same rule; before, any range was kept.
  - Kept: one-piece patterns (`%OB%`, `SMI%`, `SMITH-JONES%`, `O'BRIEN%`, `%ZZ%TEST%`), one-piece exclusions (`NOT LIKE '%TEST%'` on any name field; a two-piece one, `NOT LIKE '%TEST%PATIENT%'`, is refused, as the file would hold a name), and bounds or patterns on where one name starts (last names from A to L, on the last-name or the full-name field, which sorts LAST, FIRST).
  - Known gaps: a compound surname with spaces (`DE LA CRUZ%`) and a wildcard inside one surname (`O_BRIEN%`, `SM_TH%`) read as two pieces and are refused. A pattern on the full name and one on the last name count as two.
- Values outside the queries' own filters are judged too. The default values of the layout's runtime prompts (DA2 escapes them twice inside the layout) go through the same rules, and a text in them is read as XML when its first `<` comes after nothing but spaces, control characters and a byte order mark (Java trims a text, and its parser skips a BOM). A layout expression on a patient field is refused when a literal value sits in the field's clause, or in a clause with no column or parameter of its own. Each filter, highlight or map rule is judged with its values, and every other expression on its own: a binding's or computed column's (`hit = dataSetRow["Person Id"] == 123`, which a rule then only reads), a visibility rule's, an aggregation's filter. Outside a filter, highlight or map rule, only a clause that tests something counts (a comparison, `in`, `case`, a `BirtComp` call, a call such as `match`, `indexOf`, `startsWith` or `equals`, arithmetic on the field itself, as in `row["Person Id"] - 12345678` or `% 12345678`, or a condition, the clause before `&&`, `||` or `?`), and clauses split at `?` and `:` too. A visibility rule and an aggregation's filter are tested for their truth, so every clause of them counts: `"FIN: " + row["Enc Financial Num"]`, `row["Person Name Full Format"] || "Unknown"`, `Formatter.format(row["Person Birth Dt Tm"], "MM/dd/yyyy")` and a hyperlink built from the FIN only show the field. A field's `.length` is no value of it, and neither is a negative argument (`FIN.substring(FIN.length - 4)`, `("0000000000" + MRN).slice(-10)`). A `replace` or `split` counts its pattern (its first argument) and what it is called on (`"DOE, JANE".split(NAME)`), not its other arguments: `NAME.split(",")[1] + " " + NAME.split(",")[0]` and `String(FIN).replace(/(\d{3})(?=\d)/g, "$1-")` show the field, `NAME.replace("DOE, JANE", "CONFIDENTIAL")` tests it. A regular expression's class escapes (`\d`, `\s`) are no value; a class or a count can spell one (`/^[1][2][3]…$/`, `/^1{8}$/`), so they count.
  - Clauses split at `&&` and `||` outside brackets and strings, so `row["Person Id"] == (false || "123")` is one clause, and between and inside an aggregation's arguments (`Total.countDistinct(row["Enc Id"], row["Age at Disch"] >= 65)` counts encounters and filters on the age).
  - Comments are not read, strings take any escape (a line continuation too), and a `/` after `typeof` or `return` starts a regular expression, so a quote in a comment (`/* " */`) or after `typeof/"/` can't hide the real value as code. A `//` comment ends at a carriage return as at a line feed (before, `true // note` then a CR hid the whole filter after it), and a keyword after a dot is a member with a comment between too (`x./**/throw / 2` divides; it read as a pattern that hid the filter after it). A `/` inside a regular expression's `[class]` doesn't end it, a `/` after a backslash, a string, a regular expression, a `.` or a member named like a keyword (`x.return / 2`) divides, a comment between leaves that as it was, and a regular expression left open on its line leaves that line's other slashes as divisions. One walk finds them: no text costs more than its length (an unclosed string of escaped quotes took 45 s, and escaped slashes 95 s).
  - Refused with a reason: JavaScript DA2 doesn't write that reads more than one way: an HTML-style comment (`<!--`, `-->`), a template string (a backtick), and a `/` that is a division or a regular expression by what the reader can't see (after `}`, `++` or `--`, `yield`, `await` or `of` (a name, except in a `for … of`), right after `if`, `while`, `for`, `with` or `let`, or after the `)` of their `(`, as in Rhino's `catch (e if /…/)` and `let (…) /…/`; after any `)` in an expression with `function`, `get`, `set` or an object literal in it, as in Rhino's expression closure `function () /…/` and Rhino 1.7.14's method `({m() /…/})`. A `{` opens a block at the start, after `{`, `}`, `;` (outside a `for` head), `=>`, `else`, `do`, `try` or `finally`, or after the `)` of an `if`, `while`, `for`, `for each`, `with`, `switch` or `catch` head (`each` without `for` is a name: `new each(1) {…}` builds an object), and an object literal anywhere else, so a comment before it, a `for (;…;)` head, Rhino's `let (…) {…}` and a `catch (e if {…})` guard don't hide one; after a name and a line end, where JavaScript may end the statement, as after `var x`, `break` or `debugger`; after a keyword that follows a number's dot, as `0. in` or `0.` then a line that starts `if (…) /…/` or `for each (…) /…/`), a `<` where an operand starts or after a name and a line end (an XML literal, in Rhino), an invisible (Unicode format) character or a DEL anywhere (Rhino drops them as it reads, so `*<U+200B>/` ends a comment and `x<DEL>in` reads as `xin`), a non-ASCII character or a backslash in code outside strings and patterns (`r\u006fw`, U+2028), a backslash before a line end (Rhino 1.7R3 runs a pattern on past it), a spread (`...`, which Rhino doesn't read), a number glued to a name (`0in /…/`: Rhino ends the number and reads the keyword), E4X's wildcards and attributes (`x.*`, `x.@a`, `ns::*`, whose `*` is an operand), and a column or parameter reference that starts or ends inside a string (`['row[', 12345678, ']'][1]` read as a column named `, 12345678, `, which hid the value). None of the real exports has any. Known gap: a division or a comparison split across lines after a name (`x` then a line that starts `/ 2`), a keyword member after a name ending in a digit (`x1.in / 2`), `of`, `each` or `let` used as a name before a `/`, a division after a bracket in an expression that defines a function, names `get` or `set`, or holds an object literal (`(a + b) / 2` there; a block's `{` is no object), and `2.*3`, are refused too.
  - A literal is a string (quoted, single-quoted, a backtick template, a `constant` value), a regular expression or a number in any spelling (`0xBC614E`, `.12345678e8`). One-character pieces of a clause count together (`"1" + "2" + "3"`), and so do one-character parameter defaults. A report parameter's defaults count as a literal, counted once for the file (a long default read again for every clause took 82 s, and a bare `params` adding up every parameter for each clause 30 s), (`params["p"].value`, `params.p.value`, `reportContext.getParameterValue("p")`) unless it is a catch-all (`ALL`, `ANY`, `NONE`, `*`), and a test that a parameter is unset or a catch-all (`params["p"].value == "ALL"`, as Endexis writes) is no literal.
  - However the comparison is spelled: `eq "123"`, `BirtComp.equalTo(row["Person Id"], "123")`, `String(row[...]) + "" == "123"`, a `match` on `/^SMITH/`.
  - The field counts through a binding, computed column or data set alias that reads it (`String(dataSetRow["Person Id"])`), from a nested table (`row._outer`), and with spaces in the reference (`row . _outer ["Person Id"]`). An aggregation binding reads its arguments (`MAX` or `FIRST` of `row["Person Id"]`), but a count or a rank holds none of their values. A sum, an average or an NPV of one row is that row's value, so those read it. A binding or computed column holds its literals for any expression that tests it (`tgt = "12345678"`, one of type `constant`, or one that reads a column), labels it joins on with `+` too, since a test can split a label back out. So `d = row["Person Id"] + (-12345678)`, `+ Number("-1234" + "5678")` or `+ "-12345678"`, tested with `row["d"] == 0` or split back apart, is refused, and so is `"FIN " + row["Enc Financial Num"]` tested with `!= ""` (a known gap). It passes on what the bindings it reads hold (`String(row["tgt"])`), and `dataSetRow["cc"]` reads a computed column `cc`. A count of patients holds nothing, whether an aggregation function or a `Total.countDistinct(…)` call (a percentage of two counts is kept). Only BIRT's own `Total` counts: `x.Total.count(…)`, `x. Total.count(…)`, `$Total`, or a `Total` the code defines or assigns, is read as any other call. Code that could give `Total` a value of its own ends the exemption for every expression in the file: `Total` named other than in a call (`a = Total = …`, `with ({Total: …})`, `this["Total"]`, in a layout script too), code run as text, or a member read by a computed name (`[][k][k]("Total = …")`). A count with a regular expression in it is judged like any other expression. Each definition of a name is judged on its own, so a computed column called `tgt` that reads a column doesn't clear a binding `tgt = "12345678"`. A column read by a computed name (`row[3]`, `row["Person" + " Id"]`), or the row object read some other way (`(row)["Person Id"]`, `[row][0]`, `r\u006fw`), could be any, so it counts as a patient field, and so does code run as text or through the global object (`eval("dataSet" + "Row")`, `reportContext.evaluate`, `Function`, `this`, `globalThis`, `with`, `constructor`, a `\u` escape), and a member read by a quoted or computed key (`[]["con" + "structor"]`), or by any key on a value that is no name (`[][k]`, `f()[k]`, `""[k]`, `1[k]`; DA2's own lookups are `strength[id]`). A name the code gives a string (`var COL = "<id>"; row[COL]`, as DA2 scripts do) reads that column only when the string is its whole value (`var C = "" + "Person Id"` is not) and it is named nowhere but there and in column reads (as a member or after `...` too); a name a loop, a `catch`, a parameter, a destructuring, a spread or a second assignment could set reads any column. What the substitution adds is charged as expression text, and code it would grow past its own length (a long string read by many columns grew one expression 700-fold, 14 s) is judged as written.
  - A rule that assigns or defines a function (`(v = row["Person Id"]) …`, `var x = …`) gets no exemption: any literal in it counts against any patient field.
  - Kept: a blank, one character or a run of Zs (`== ""`, `!= null`), a style or a map rule's display text (`#991B1B`, `10pt`), and an age worked out from the birth date (`BirtDateTime.diffYear(row["Person Birth Dt Tm"], BirtDateTime.today()) >= 18`, in either form, or a binding that subtracts it from another data set date; a binding or computed column of the report's own, which can hold a constant, makes no age). The age exemption is for birth-date fields only. An age in days (`diffDay`) is refused: it can pick out the date.
  - Each rule is read once, a nested one with it (an expression inside another is part of it), each scan is one walk (a long run of spaces after a `[` was quadratic), only the code that is judged is searched for column reads, one pattern finds every assignment, and a chain of bindings that pass a column on is followed once (21.7 s before). A rule over 20,000 characters, or a layout whose expressions run past 200,000 in all, is refused (DA2's real ones: 589 and 22,000 at most). Crafted rules took up to 30 seconds to read; the worst crafted file under the caps now takes 1.2 s at 1 CPU, about what it is charged, and crafted texts for the new scan (all quotes, open comments, slashes, brackets, aggregation commas, arithmetic, nested or chained pattern calls, labels, counts, an unclosed regular-expression count, thousands of bindings each read by others) 0.2 s at most.
  - Known gaps: a layout script, a value in a text item's HTML, an expression that puts the value in another column's clause (or another argument of a call), a ternary that reuses a tested parameter's default, an age to the day worked out by hand, a test written without an operator or test call outside a rule list (an object lookup) can still hold or pick out a value. An `&&` or `||` inside plain brackets is one clause, so `(name != null && unit == "4 WEST") ? 1 : 0` is refused, and so is a bracketed test inside a concatenation (`"FIN: " + FIN + (unit == "4 WEST" ? "*" : "")`). A birth date compared with a cutoff date (`dob > row["cut18"]`, or `BirtDateTime.addYear(...)` inline) a cut at a found character (`name.substr(name.indexOf(",") + 2, 30)`) a `replace` of two or more characters (`NAME.replace(" JR", "")`), a replacement's text when another `replace` or `split` is called on the result, a letter range in a regular expression (`[A-Za-z]`), and arithmetic beside a patient field in a shown expression (a balance negated beside the name, `(String(FIN).length) - 4` in brackets, an age worked out by hand from the birth date) are refused too, and so is a test on a binding that holds more than a label (`NAME.split(",")[1]` tested `!= ""`). A condition inside plain brackets of a shown expression can still mark a value. Java classes reached through `Packages` (`Packages.java.lang.Class`), code run as text in a layout script, and code that reaches `Function`, the global object or Java by a roundabout route (a key held in a variable on a named object, `Number[k]`, `Object.getOwnPropertyDescriptor`, `__parent__`, `getClass`) can still read a column unseen: a deliberate insider's route, like a value in a text item's HTML. A list of the names code may use isn't workable (real reports call hundreds of their own). A binding that joins a constant to a column it then cuts to nothing (`"12345678" + String(row["Enc Type"]).substr(0, 0)`) passes no literal on.
- `remove_column` removes the column's cells wherever its table shows it (a column shown twice lost only one cell, leaving the other's data with no binding). It refuses with a reason when its cell holds other fields or a nested grid, or when a group or header row's cell at its place holds another field (removing `Enc Loc Facility` from the census deleted the unit's average stay). When the layout can't be changed, the refusal names what uses the column, or says the layout shows it.
- `DA2Files.size` is the files' unzipped size in bytes, which a change walks, and `DA2Files.work` counts what reading them took, the same way every time: a quarter per byte, 10 per XML element (the runtime prompts' embedded XML too, and 10 per attribute and 100 per text parsed there), 10 per distinct attribute name in a member, 5 per character of layout expression, 20 per rule, 30 per clause or rule value judged, 40 per attribute of a filter value, 50 per filter and 7 per character of its field's names, 80 more per filter on a name field with 15 per value and 8 per character of each (split into pieces however long it is: a value of 450,000 one-digit runs cost six times its charge, and thousands of short name filters 2.6 times), 60 per binding or computed column and 3 per character of the binding and column names judged (18 per character of a name not in ASCII, which NFKC may spell out 18 times longer: 600 names of U+FDFA cost 10.7 times a charge by length), in units of about 0.1 µs on one CPU (measured: 0.023 µs a byte, up to 1.4 µs an element, 0.5 µs a character). `DA2FileError.work` is what a refused read had counted when it stopped, so a caller can charge it (a file refused for a patient filter cost 0.4 s of reading on every turn, uncharged).
- More catalog fields count as patient identifiers: any person, patient or encounter id that isn't a clinician's, a sender's or an organisation's (`Sch Pat Person Id`, `Ib Rx P Patient Id`, `CE Enc Id`), the home address string, the encounter's `Name`, and the name history's last name (`Name Hx La`). Field names are matched with Latin lookalikes from other scripts folded, so `PI Alias Type`, which the catalog spells with a Cyrillic letter, is a code again.
- `text_match` also judges the pattern as typed: `smith john%` on Person Name Last is written `SMITHJOHN%`. It keeps the name filters it judges from the read, so a change no longer walks every filter in the file (0.1 s an ask on a crafted 2 MB file, now under 1 ms).
- A rule's values nested inside one another (a `value1` list inside a `value1`) are each read once: 195 nested lists of 5,000 values took 83 s. Working out an expression's pieces and blanked copies, and finding its column reads and following each one, is counted where it is done (layouts dense with birth-date reads cost three times their charge): the checks read each expression in up to eight spellings, and dense ones (`a/a/a…`, `a(a(…`, `""""…`) cost 5 to 10 times their charge at 1 CPU. Each read keeps them in a cache of its own thread (the chat reads up to three files at once, and one emptying a shared cache made another work them out again uncharged), emptied after each member and past about 30 MB (a string-dense upload grew memory by 105 MB), and a read stops once working them out passes 5,000,000 units (0.5 s; a real export takes under 90,000). A long name given a short value no longer takes characters off the layout's total (95 expressions of 19,000 characters were read past the 200,000-character cap).
- Reading a deep nest of filters judges each value once, in the filter it belongs to. Before, every enclosing filter judged it again: a crafted file took 20 seconds to read.
- `files()` gives each member its new ids in one pass, and deflates at level 1 (about twice as fast as the default on layout XML, for a zip about a third bigger), which a change's charge covers. Before, it ran one substitution over every member per id, so a file of 19 queries took 5–7 times what writing it was charged.
- `summary()` lists the first 100 columns and the first 100 filters of each query, with a count of the rest. A forged query of 20,000 columns made a 6.8 MB reply.
- A refused read is charged what it parsed before the refusal (`DA2FileError.work`): 10 for each element and attribute of a member it could have parsed, 10 for each `<`, `=`, `lt;` and `#` of an embedded prompt (a `&#60;` is a `<` one level down), and 5 for each character of layout expression measured, so a crafted file refused at its last step can't cost more than its charge.
- `remove_column` looks for references to the column with one pattern. Before, it had one alternative per binding name, and a file with thousands of bindings took over a minute.
